## Readiness is a state transition

The source procedure bootstraps a run at `READY_FOR_G1_VALIDATION`, resolves parameters and profiles, then freezes source contracts/cutoffs. Repeated pre-acceptance snapshot construction must reproduce the three hashes. Positive checks move the run to `G1_VALIDATED`; the acceptance finalizer alone moves it to `G1_READY` and the population to `READY_FOR_GENERATION`.

The source rows are labeled `CONTRACT_READY_PRE_GENERATION`. **That is a statement about an approved source interface, not proof that POS or deposit observations have already arrived.** G1 must not generate merchants, applications or time-series facts.

## Why failure behavior matters

A missing parameter is not an invitation to choose a convenient default. An ambiguous parameter is not resolved by row order. A missing source contract is not repaired by using an unregistered source. The three named negative controls are `G1_NEG_01_MISSING_PARAMETER_REJECTED`, `G1_NEG_02_AMBIGUOUS_PARAMETER_REJECTED` and `G1_NEG_03_MISSING_SOURCE_REJECTED`.

These controls establish the configuration boundary later generators rely on. Frozen snapshot rows are not edited manually, and snapshot construction is not a normal rerun after `G1_READY`. Recovery and current build eligibility require their own source-defined conditions.

## How to inspect it

Compare the run registry context, the parameter/profile/source snapshot hashes and the master report together. A matching population name without matching configuration is insufficient. The detailed report separates run acceptance, profile/source rows, scope summaries and resolution errors so a reviewer can locate the cause of a stop rather than infer it from the final status.
