# M1.3 · Application and requested structure

**What did the merchant ask for before any affordability decision?**

> **Source basis:** original `v0.2R1_ACCEPTED` in `Module_1/1.03_Application_and_Requested_Structure`. This is the retained foundation/Module 1 basis; no Module 1 technical payload is changed by the R26 successor. This is a reading companion, not a new technical acceptance or execution guide.

M1.3 creates a financing request—not a favorable offer disguised as an input. It connects amount, remittance share, payback multiple, horizon and use of proceeds, while deliberately allowing requests that later assessment may reject or restructure.

## One request per accepted merchant

Exactly 750 applications are created, one for each accepted merchant. The application key extends the stable merchant key with `_A01`; application and as-of dates use the run date. These are application records, not 1,500 independent applications: the scenario split arrives in subsequent evidence and decision layers.

The accepted horizon mix is 188 requests at 30 days, 337 at 60 days and 225 at 90 days. The quota method and deterministic rank assignment preserve that exact mix. Use-of-proceeds categories are assigned through the same controlled approach.

## Terms belong together

The request generator resolves a synthetic annual-sales proxy from the merchant's sales band. **That proxy exists to generate internally related request terms; it is not observed cash-flow evidence and must not become an underwriting feature.** M1.9 later derives actual governed features from the retained daily panel.

Four amount limits compete: request appetite, sales-linked reference, funding-to-annualized-sales cap and global maximum. The selected request applies the lowest limit, rounds down to a $100 increment and respects the product minimum. When the minimum overrides a lower structural candidate, the blueprint explicitly labels `MINIMUM_PRODUCT_AMOUNT_FLOOR`; it does not call that amount affordable.

```text
Requested total repayment = round(requested funding × payback multiple, 2)
Requested finance charge = total repayment − requested funding
Daily request-path measure = total repayment ÷ requested horizon
```

The remittance percentage is a sales-linked share, the payback multiple is a repayment factor, and the horizon is measured in days. They cannot be interchanged. The implied payoff and repayment-path ratio use the request-generation sales proxy only to diagnose conservative/aggressive requests.

## Why a failed validation did not require a new population

The first relationship-differentiation test used unmatched cohort averages of final funding-to-sales ratios. Size, horizon, purpose mix and the minimum floor could obscure the direct relationship-stage control. The accepted correction tests `request_path_utilization_factor` instead and retains the raw ratio as a diagnostic.

`M1_3_POS_36_RELATIONSHIP_DIFFERENTIATION` is therefore a useful example of validating the parameter's actual mechanism rather than demanding that an uncontrolled aggregate move in a preferred direction. The 750 generated requests stayed unchanged through that validation correction.

## Handoff and exclusions

M1.4 treats the accepted request set as an integrity prerequisite, not a sales-generation target. Capacity, risk, economics, counteroffers and authority belong to later stages. An above-reference request is not automatically a decline; an on-reference request is not an approval.
