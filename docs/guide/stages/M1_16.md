# M1.16 · Acquisition attribution and merchant acquisition cost

**Where did the application come from—and which acquisition costs should be counted once?**

[Stage map](../../README.md#stage-map) · [Which source version?](../SOURCE_VERSIONS.md) · [Current use](../CURRENT_USE.md)

> **Source basis:** original `v0.2R3_ACCEPTED` in `Module_1/1.16_Acquisition_Attribution_and_CAC`. This is the retained foundation/Module 1 basis; no Module 1 technical payload is changed by the R26 successor. This is a reading companion, not a new technical acceptance or execution guide.

M1.16 adds commercial context to the accepted evidence foundation. It distinguishes the source/campaign that acquired an application, the funnel burden behind that acquisition, incurred cost and conditional-on-funding cost. Attribution is descriptive and allocative—not causal marketing effectiveness.

## An acquisition companion, not a replacement risk contract

The accepted `M1_ACQUISITION_CONSUMPTION` v1 / `M1_ACQUISITION_SCHEMA_V1` contract has **750 application-level latest rows and 750 archive rows**. Joining it to the scenario-qualified M1.15 contract yields 1,500 integrated rows. The acquisition facts are not invented again for each scenario.

The source preserves five parent channels and defines 18 normalized source profiles and 20 campaigns. Six aggregate funnel stages end at `APPLICATION_SUBMITTED`. Nonapplicants are represented in campaign aggregates, not materialized as personal prospect records.

## Touchpoints do not manufacture attribution precision

Every application has one to three touchpoints. Exactly one primary touch has weight 1.0; assisted touches have weight 0.0. Evidence status propagates from source/campaign to touchpoint and attribution. This is an explicit primary-attribution method, not a claim of multi-touch causal credit or modeled incrementality.

Submitted campaign counts reconcile exactly to the 750 accepted applications. A source can have a different cost profile without changing the accepted merchant population or deciding which applications are approved.

## Allocate costs in cents and reconcile the ledger

Each campaign has an incurred/allocated line and a conditional-on-funding line. Incurred costs are allocated only to primary-attributed applications. Whole cents are distributed by deterministic quotient/remainder order on application ID.

That allocation makes the physical sum exact instead of leaving a rounding residual. Conditional cost remains conditional; it must not be presented as incurred on every submitted application or as an actual payment to a marketing partner.

## Reconcile the existing economics before adding detail

M1.14's acquisition rate/amount is verified scenario-invariant and inherited once per application. M1.16 separately exposes detailed cost, supported overlap, unmapped legacy proxy, incremental cost beyond M1.14 and enhanced total if booked.

Where attribution or overlap is blocked, unsupported overlap/incremental/enhanced totals stay null. Known components remain visible. **Unknown cost is not zero cost**, and a supported zero requires an explicit basis. This prevents detailed attribution from becoming a second unqualified expense layered over the original proxy.

## Handoff to G2 and analytical segmentation

M1.17 certifies this companion alongside the core application contract. Power BI and portfolio analysis can then segment by acquisition context with source-owned keys and costs. Neither channel totals nor acquisition correlations demonstrate a causal campaign effect, a production funnel or an executed scaled campaign.

## Requirements interpretation

The following are editorial reading locators into the retained requirements/design/authority documents—not invented native requirement IDs. Native IDs and control lists remain in the linked originals.

**Design · Funnel and attribution.** Keep submitted counts, primary/assisted weights and propagated evidence status explicit.

**Design · Cost allocation.** Distribute whole cents deterministically so application allocations reconcile to campaign ledgers.

**Design · M1.14 bridge and evidence gates.** Identify supported overlap before adding cost; preserve null unsupported totals.
