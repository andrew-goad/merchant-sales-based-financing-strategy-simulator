Root cause

The M2.8 retry-settlement amount used the following rounding order:

ROUND(
  ROUND(exposure / duration, 2)
  × payment_factor
  × retry_multiplier,
  2
)

For the affected account:

ROUND(4699.37 / 14, 2) = 335.67

Scheduled event:
ROUND(335.67 × 0.75, 2) = 251.75

R12 retry event:
ROUND(335.67 × 0.75 × 2, 2) = 503.51

The retry calculation multiplied the unrounded factor result before applying the final cent rounding. The corrected calculation rounds the scheduled cent amount first:

ROUND(
  ROUND(
    ROUND(exposure / duration, 2)
    × payment_factor,
    2
  )
  × retry_multiplier,
  2
)

That produces:

ROUND(251.75 × 2, 2) = 503.50

The seven-event processed total then becomes exactly $1,762.25, restoring:

processed = scheduled − returned + retry

and the correct ending exposure of $2,937.12.

Why the correction belongs in M2.8

M2.9 is correctly enforcing exact reconciliation. Introducing a one-cent tolerance would conceal a deterministic generation defect and weaken account-certification evidence.

It would also fail to solve the downstream recurrence correctly. M2.10’s ACTIVE_RECONCILED mapping properly requires:

processed payment = scheduled payment
returned payment  = retry payment
reconciliation variance = 0
exposure variance       = 0
exception resolved
unresolved exception count = 0
certified active state

R13 therefore preserves the exact-zero M2.9 and M2.10 contracts and changes only the lowest correct layer: the transformed M2.8 retry-settlement generation expression.

R13 architecture

R13 is a clean compiler/final re-performance from immutable R6. It does not resume, rewind, repair, or execute the retained R12 compiler because the corrected M2.8 bytes necessarily change downstream hashes and predecessor bindings.

The runtime:

  1. Verifies the exact retained R12 result ZIP and SHA-256.
  2. Verifies all accepted-source hashes and R9/R13 configurations.
  3. Fingerprints immutable R6.
  4. Connects to the retained R12 compiler under PostgreSQL default_transaction_read_only=on.
  5. Requires the exact R12 checkpoint and one-row failure population.
  6. Creates a fresh R13 compiler clone from R6.
  7. Executes M2.5–M2.10 and all successor controls.
  8. Drops the compiler only after the complete compiler path passes.
  9. Creates a second fresh clone from R6 and re-performs the exact compiler-transformed bytes.
  10. Requires exact compiler/final normalized-receipt and database-derived identity equality.
  11. Re-fingerprints R6 and R12 and fails if either changed.
  12. Retains the successful final R13 database and produces a result ZIP and sidecar.

The accepted source SQL files remain byte-for-byte unchanged. The correction is applied through a versioned, hashed successor transform. R9 terminal-state comparison semantics and R12 nullable-hash semantics remain unchanged.
