# M2.5 Program 167 diagnosis

The single failure is a **validation-only defect**, not a defect in the population generated by Program 166.

The source audit isolates the failed control to:

```text
M2_5_POS_082_LATEST_ARCHIVE_REPRODUCTION
```

## Exact cause

Program 166 constructed each immutable archive payload from the target-typed staging version of the latest contract:

```sql
to_jsonb(latest) AS contract_payload
```

That staging table intentionally does **not** contain the system-managed database column:

```text
created_at
```

When the row was inserted into the persistent latest table, PostgreSQL populated `created_at` through the table default.

Program 167 v0.2 then incorrectly compared the archive payload to:

```sql
to_jsonb(l)
```

That expression includes the persistent latest row’s `created_at` value. It therefore reports all 59 latest/archive rows as payload mismatches even though every governed business, monitoring, lineage, and contract field matches.

The correct comparison is:

```sql
a.contract_payload IS DISTINCT FROM
    (to_jsonb(l) - 'created_at')
```

Programs 169, 170, and 171 already use this correct comparison. Only Program 167 was inconsistent.

This fully explains:

```text

1 FAIL
```

# M2.5 Program 168 diagnosis

This is a **code-formatting defect in the diagnostic text for Negative Control 020**, not a failed control and not a defect in the M2.5 population.

Program 168 reached:

```text
M2_5_NEG_020_SERVICING_NOTICE_PAYLOAD_VOCABULARY
```

and attempted:

```sql
format
(
    'collection %, write-off %, restructure %, notice %, adverse-action %',
    v_collection_rejected,
    v_writeoff_rejected,
    v_restructure_rejected,
    v_notice_rejected,
    v_adverse_rejected
)
```

PostgreSQL `format()` requires a valid conversion after every percent sign, such as `%s`, `%I`, or `%L`. A literal percent sign requires `%%`. Here, the first `%` is followed by a comma, so PostgreSQL reports:

```text
SQLSTATE 22023
unrecognized format() type specifier ","
```

The screenshot hint about `%%` would only print literal percent signs. This code intends to display five Boolean values, so the cleaner correction is to replace `format()` with `concat()`.

## Exact source inconsistency

Program 166 generated the portfolio summary’s `active_advance_count` as a **start-of-day operational count**:

```sql
count(*) FILTER
(
    WHERE receivable_balance_before > 0
)
```

Program 169 v0.2 attempted to reproduce that field using:

```sql
count(*) FILTER
(
    WHERE NOT paid_off_flag
)
```

Those are not equivalent.

An advance that pays off during a particular day has:

```text
receivable_balance_before > 0    true
paid_off_flag                    true
```

It was active at the beginning of the day and paid off by the end of the day. Program 166 therefore correctly includes it in both:

```text
active_advance_count
paid_off_count
```

The original Program 169 excluded it from `active_advance_count` because it used the end-of-day `paid_off_flag`. That creates a portfolio-summary mismatch on each payoff-event day and causes:

```text
acceptance_status = FAIL
```

The generated portfolio summaries are correct. The acceptance-time reproduction was wrong.
