A clean 750 replay proves several things before we introduce the additional variable of a new population size:

- the campaign harness has been rebased correctly to v2.1.0;
- the reconstructed source order executes the same semantics;
- no stale pre-R26 source slipped into the campaign plan;
- configuration propagation is correct;
- `module1_run_id` lineage still works;
- checkpoints and reports are being captured correctly;
- isolation/database orchestration is not changing results;
- no hidden environmental dependency has appeared.

That makes the 2,500 run much easier to interpret.

If the 2,500 run later produces an unexpected outcome, we know it is much more likely to be related to **fresh-population behavior or scale**, rather than a broken harness.

Without the 750 replay, those two causes are confounded.

## I would make the 750 gate very strict

The 750 step should be an **equivalence certification**, not another exploratory campaign.

I would define three classes of fields:

| Class | Expected result |
|---|---|
| Business/data outputs | **Exact zero differences** |
| Deterministic IDs/hashes derived from governed inputs | **Exact zero differences** |
| Execution metadata such as timestamps, runtime durations, filesystem paths | Expected to differ and explicitly excluded/normalized |

So “zero changes” should mean **zero semantic/deterministic output differences after excluding explicitly non-comparable execution metadata**.

We should define that exclusion list *before* the run, not after seeing discrepancies.

### I would also compare more than final tables

Ideally the reconciliation should cover:

- row counts at governed stage boundaries;
- keys and populations;
- application/scenario assignments;
- evidence/capacity/economics outputs;
- candidate structures;
- final decisions and reason codes;
- authorized funding population;
- funded amounts/terms;
- monitoring and servicing outputs;
- reconciliation/account-state outputs;
- report/checkpoint cardinalities;
- financial aggregates;
- hashes for canonical exported results where feasible.

That gives us a much stronger statement than “final decisions matched.”

## This also resolves the old “controlled divergence” issue

The prior Campaign handoff advised distinguishing non-regression equivalence from expected controlled divergence because the corrected counteroffer logic legitimately changed some merchants relative to the **old strategy**.

That was the right rule for:

> old predecessor strategy vs corrected strategy.

But once we establish the **current v2.1.0 750 population as the reference**, there should no longer be expected strategy divergence.

We are no longer testing:

> Did R26 change the old results correctly?

That has already been answered.

We are testing:

> Can the campaign harness reproduce R26/v2.1.0 exactly?

For that test, **zero semantic differences is the right standard**.

## Revised weekend sequence

I would now make the progression:

**1. Rebase/preflight**  
Bind published v2.1.0, rebuild current source plan, rebase campaign configuration, establish isolated target.

**2. 750 deterministic golden replay**  
Run the known 750 cohort end to end.

**3. Full 750 reconciliation**  
Require zero semantic/deterministic differences versus the accepted v2.1.0 reference.

**4. Gate decision**  
If zero-diff passes, authorize fresh 2,500.

**5. Fresh 2,500 performance shakedown**  
New deterministic population identity and seed; same accepted business logic.

**6. 2,500 validation and performance analysis**  
Cardinality, lineage, decision coherence, lifecycle, reconciliation, timing and resource growth.

**7. 25,000 readiness decision**

That is actually a **cleaner audit story**.

The resulting narrative would be:

> The rebased Campaign harness first reproduced the accepted 750-merchant v2.1.0 reference with zero semantic differences, then successfully generated and processed a fresh 2,500-merchant population through the same end-to-end business logic.

That is considerably stronger evidence than going straight to 2,500.

So I would revise my earlier recommendation: **yes, do the 750 replay first—but make it automated, exact, bounded, and fast.** It should be a certification gate, not another development workstream.
