Blocker 1 — The deterministic hash preimage model is currently circular

The WP1 specification correctly requires physical-field reconstruction, ordered set hashing, exclusion of M2.11 audit timestamps, and lifecycle-only updates after generation. [export reference: filecite | turn44file1]

The problem is in M2_11_TYPE_PRECISION_DICTIONARY.csv: its single hash_inclusion column is being used ambiguously. My direct audit found that all 19 hash-output fields are marked YES, including:

16 row_hash fields
2 contract_row_hash fields
1 archive_row_hash field

The registry also marks all of the following YES:

registry_id
contract_status
contract_set_hash
combined_set_hash
row_hash

This cannot be implemented literally:

  • a row_hash cannot include itself in its own preimage;
  • contract_set_hash depends on the registry row hash, so including it in that row hash creates a cycle;
  • combined_set_hash depends on the object-set identities, including the contract set, creating another cycle;
  • contract_status changes from GENERATED to VALIDATED to ACCEPTED, but Programs 215 and 217 are prohibited from rebuilding the registry’s immutable identity;
  • generated surrogate IDs are unsafe deterministic inputs because PostgreSQL sequences are not rolled back transactionally.

This is not merely theoretical. The accepted project convention explicitly reconstructs a registry hash after excluding:

registry_id
contract_status
generated_at
validated_at
accepted_at
row_hash
created_at
contract_set_hash
combined_set_hash

That pattern is visible in the accepted M2.1 validation and recovery source. [export reference: filecite | turn46file6] [export reference: filecite | turn47file0]

Required correction

WP2 should implement this exact separation:

Ordinary canonical rows

Exclude from the row-hash preimage:

the row_hash field itself
M2.11-created created_at / updated_at timestamps
generated surrogate identity fields

Copied accepted-source timestamps may remain when they are intentionally part of lineage; only new M2.11 audit timestamps are excluded.

Latest contract

Compute contract_row_hash from the physical latest row excluding:

contract_row_hash
created_at

Archive

archive.contract_row_hash
=
latest.contract_row_hash

Compute archive_row_hash from:

contract_payload
copied contract_row_hash
module1_run_id
contract_version
strategy_profile_code
reporting_scope_code

Exclude:

archive_id
archive_row_hash
archived_at
created_at

The “archive identity” should mean the governed business identity—not the generated surrogate archive_id.

Contract registry

Compute the registry row hash from the physical registry row excluding:

registry_id
contract_status
generated_at
validated_at
accepted_at
row_hash
created_at
contract_set_hash
combined_set_hash

The remaining object counts, source identities, source hashes, and the preceding object-set hashes may participate.

Then calculate:

registry row hash
→ contract_set_hash
→ combined_set_hash

in that order.

Policy profile

configuration_hash should be calculated from configuration_payload. It must not be treated as an input to its own calculation.

Dictionary treatment

The cleanest repair is to stop asking one Boolean field to represent two different ideas:

row-hash preimage inclusion
≠
object membership in a set hash

WP2 should either:

  1. revise the dictionary to use separate concepts, such as row_hash_preimage_inclusion and set_hash_membership; or
  2. add an authoritative M2_11_HASH_PREIMAGE_SPECIFICATION.csv that explicitly enumerates the preimage for every hash-producing object.

I prefer the second option during an in-progress WP2 build because it is bounded, auditable, and does not require redesigning all 1,014 dictionary rows.

Blocker 2 — An uncataloged hash helper is referenced

The type dictionary defines the policy configuration hash as:

m2_11_hash_jsonb(configuration_payload)

But the 42-object physical catalog contains only one M2.11 function:

msbf_ctl.m2_11_block_archive_mutation

There is no cataloged:

msbf_ctl.m2_11_hash_jsonb

and no cataloged registry-hash helper.

That leaves WP2 with a dangling implementation dependency.

Recommended resolution

Program 212 should explicitly define and catalog:

msbf_ctl.m2_11_hash_jsonb(jsonb)
msbf_ctl.m2_11_registry_row_hash(jsonb)

The second helper should implement the registry exclusions above.

This would increase the noncanonical physical-object catalog from:

42 → 44 objects

but it would not change:

19 canonical object families
19,298 canonical entities
any frozen grain
any frozen business semantic

The alternative is to remove the helper reference and write every hash expression inline. That is valid but less desirable because generation and independent validation could drift. Given the accepted project pattern, defined helper functions are safer.

No helper function should be created silently outside the physical catalog.

Important issue folded into Blocker 1 — Surrogate IDs

These three fields are currently defined as non-null bigint, have no derivation rule, and are marked as hash inputs:

policy_profile_id
archive_id
registry_id

WP2 should preserve them as physical surrogate identifiers if desired, but exclude them from deterministic hashes.

There is no reason to let a sequence value determine the canonical identity of a policy, archive, or registry record. The deterministic identity already exists in the business keys:

Policy:
module1_run_id or policy_code / methodology version

Archive:
run + contract version + strategy + scope

Registry:
run + contract version
